## Purpose and baseline

Build a durable contribution habit in a small number of healthy repositories. Learn to understand unfamiliar code, find useful work, deliver scoped changes, and collaborate through review.

## Capability progression

Stages describe increasing independence, not courses to finish. One real attempt can produce evidence for several stages; revisit only gaps that the work exposes.

| Stage | Capability | Evidence to move forward |
| --- | --- | --- |
| S1 — Contribution workflow | Explain the upstream/fork/local branch relationship and the change → validation → PR → review loop | Demonstrate a local branch/change/diff and explain what would be submitted, where, and why; no practice PR to a stranger |
| S2 — Codebase navigation | Evaluate a repository, run it, and trace a small behavior through relevant files and tests | Setup/baseline evidence, a short code path in your own words, and a reproduced problem or understood change |
| S3 — First useful scoped contribution | Make the smallest coherent fix or improvement, with appropriate tests/docs and a clear rationale | Reviewable local change and validation; submit when appropriate. A merge is not required |
| S4 — Return to the same repositories | Use prior context and feedback on subsequent contributions | Linked follow-up work showing learned conventions, review responses, and less rediscovery |
| S5 — Deeper bug/feature work | Reason across relevant components and consider compatibility and alternatives | A bounded bug/feature change with regression evidence and explained design choices |
| S6 — Recurring useful contributor | Independently find worthwhile work, communicate, deliver, and follow through repeatedly | A sustained history of useful attempts and honest outcomes in a small set of repositories, including maintainer feedback when available |

By joining, aim for repeatable contribution ability and involvement worth continuing. No PR quota, tutorial-completion gate, forced merge deadline, or automatic stage pass.

## How this stays small

Follow [CONTRIBUTION_METHOD.md](CONTRIBUTION_METHOD.md). Start with one active repository and one bounded issue. Retain a healthy repository rather than repeatedly restarting the search. In maintenance, a setup/reproduction attempt can be a whole slice; deeper work earns room later. The master owns yield rules, and a sprint may omit this track.

Keep the existing stack unless the work genuinely requires otherwise. No beginner programming course, framework tourism, typo spam, swag hunting, mass AI contributions, or random issue-label collecting. Useful tests, reproductions, and substantive documentation fixes count when they address an actual need.
